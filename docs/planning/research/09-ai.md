## 0. Headline answers

### 0.1 OpenAI compatibility â€” YES, and it is the whole ballgame **[V]**

Databricks Model Serving exposes an **OpenAI-compatible API** at the workspace host. The OpenAI SDK works
directly against it by overriding `base_url`:

```python
from openai import OpenAI

client = OpenAI(
    api_key="dapi-your-databricks-token",
    base_url="https://example.staging.cloud.databricks.com/serving-endpoints"
)

response = client.chat.completions.create(
    model="databricks-claude-sonnet-4-5",
    messages=[{"role": "user", "content": "What is Databricks?"}],
    temperature=0
)
```

Source: <https://docs.databricks.com/aws/en/machine-learning/model-serving/query-chat-models>

- **Base URL shape**: `https://{workspace-host}/serving-endpoints` **[V]**
- **`model` parameter is the *serving endpoint name*, not a model ID.** This is the single most important
  quirk. `databricks-claude-sonnet-4-5` is the name of a pre-provisioned pay-per-token endpoint, not a
  model string that Databricks resolves. For a custom or provisioned-throughput endpoint you pass *your*
  endpoint name. **[V]**
- **Auth**: `Authorization: Bearer <token>`, passed as OpenAI's `api_key`. Docs recommend
  **machine-to-machine OAuth tokens (service principal) for production**, PATs for dev/test. **[V]**
  Source: <https://docs.databricks.com/aws/en/machine-learning/model-serving/score-foundation-models>
- **Compatible surfaces**: chat completions, embeddings, and vision. There is additionally an
  **OpenAI Responses API** surface at path `/serving-endpoints/responses`. **[V]**
  Source: <https://docs.databricks.com/aws/en/machine-learning/model-serving/query-openai-responses>
- Docs state Model Serving presents "a unified, OpenAI-compatible API across providers", so the same client
  code works whether the model behind the endpoint is Databricks-hosted, OpenAI, Anthropic, Cohere, Bedrock,
  or Vertex. **[V]**

**Caveat / open thread [G]:** one docs page surfaced a second base URL shape,
`https://{host}/ai-gateway/mlflow/v1`, alongside a note that foundation-model requests are now
"routed through **Unity AI Gateway (Beta)**". I could not confirm whether `/ai-gateway/mlflow/v1` is a
new preferred path, a legacy MLflow-deployments path, or a doc artefact. **Treat `/serving-endpoints` as
canonical** â€” it is the one that appears in current code samples â€” but make the base URL a config value,
not a constant. Verify before GA.

### 0.2 MLflow tracing from .NET â€” YES, via OTLP/HTTP, no Python required **[V]**

Databricks hosts an **OTLP trace collector**:

```
POST https://{workspace-host}/api/2.0/otel/v1/traces
```

Headers:

| Header | Value |
|---|---|
| `content-type` | `application/x-protobuf` |
| `Authorization` | `Bearer <token>` |
| `X-Databricks-UC-Table-Name` | `<catalog>.<schema>.<table_prefix>_otel_spans` |

Source: <https://docs.databricks.com/aws/en/mlflow3/genai/tracing/trace-unity-catalog> (page dated 2026-07-21)

This is **standard OTLP/HTTP protobuf**. The .NET `OpenTelemetry.Exporter.OpenTelemetryProtocol` package
speaks it natively â€” set the endpoint, headers, and `HttpProtobuf` protocol, and traces land in Unity
Catalog and surface in the MLflow experiment UI. **No Python, no MLflow SDK, no Databricks-specific client.**

Databricks' own announcement is explicit that this is language-agnostic and that the traced app need not run
on Databricks: "Any OTel-compatible client can export traces to this endpoint, including popular AI agent
frameworks across many programming languages"; the agent "can be running anywhere" and "can be deployed
outside of Databricks."
Source: <https://www.databricks.com/blog/observability-any-agent-anywhere-production-ready-tracing-opentelemetry-unity-catalog>
(announced **2026-05-22**, described as production-ready; ingestion is built on "Zerobus Ingest") **[V]**

**To render correctly in the MLflow UI**, spans must carry OTel **GenAI semantic convention** attributes â€”
these are standard OTel names, not MLflow-proprietary ones: **[V]**

| Attribute | Values / format |
|---|---|
| `gen_ai.operation.name` | `chat`, `text_completion`, `generate_content`, `response`, `embeddings`, `execute_tool`, `create_agent`, `invoke_agent` |
| `gen_ai.input.messages` | string, or JSON array of `{role, content}` |
| `gen_ai.output.messages` | same shape as input |
| `gen_ai.usage.input_tokens` | int (set on root span) |
| `gen_ai.usage.output_tokens` | int (set on root span) |
| `session.id` | string |
| `user.id` | string |

Source: <https://docs.databricks.com/aws/en/mlflow3/genai/tracing/third-party/otel-span-attributes>

**Why this matters for us:** `Microsoft.Extensions.AI` ships
`UseOpenTelemetry(...)` middleware on `ChatClientBuilder` that already emits GenAI-convention spans
(<https://learn.microsoft.com/en-us/dotnet/ai/microsoft-extensions-ai>). So the .NET pipeline is:
`IChatClient` â†’ `.UseOpenTelemetry()` â†’ OTLP exporter â†’ Databricks. Most of the tracing story is wiring,
not code. **[V for each component; the end-to-end composition is untested â€” see Â§8]**

**Secondary path (OSS MLflow, not Databricks-managed):** MLflow Server â‰¥ 3.6.0 exposes `/v1/traces` with
header `x-mlflow-experiment-id`, OTLP/**HTTP only** (gRPC not supported), and requires a SQL-backed store.
MLflow â‰¥ 3.7.0 accepts gzip/deflate compressed payloads. Relevant only if we support self-hosted MLflow.
Source: <https://mlflow.org/docs/latest/genai/tracing/opentelemetry/ingest/> **[V]**

Note the two paths use **different endpoints and different headers** (`X-Databricks-UC-Table-Name` vs
`x-mlflow-experiment-id`). Do not assume one config works for both.

## 3. Vector Search

Note: docs are mid-rename â€” pages appear under both `/vector-search/` and `/ai-search/`
("Databricks AI Search"). Expect URL churn.

### 3.1 Index types **[V]**
Source: <https://docs.databricks.com/aws/en/generative-ai/vector-search>

- **Delta Sync Index** â€” auto-syncs from a Delta table; requires Change Data Feed on source for standard
  endpoints. Embeddings either Databricks-managed (service computes them) or self-managed (you supply).
- **Direct Vector Access Index** â€” you push vectors via REST; no auto-sync.
- **Storage-optimized endpoints** additionally support full-text/BM25 keyword indexes with no embeddings.
- Converting self-managed â†’ Databricks-managed embeddings requires creating a new index.

### 3.2 Tenant filtering â€” YES, and this is the critical one **[V]**
Source: <https://docs.databricks.com/aws/en/vector-search/query-vector-search>

Filters work on **any column in the Delta table**, so a `tenant_id` column is directly filterable.
**The syntax differs by endpoint type** â€” this is a real trap:

| Operator | Standard endpoint (dict) | Storage-optimized (SQL string) |
|---|---|---|
| Exact match | `{"tenant_id": "value"}` | `tenant_id = 'value'` |
| OR | `{"col1 OR col2": ["a","b"]}` | `col1 = 'a' OR col2 = 'b'` |
| NOT | `{"tenant_id NOT": "value"}` | `tenant_id != 'value'` |
| LIKE | `{"col LIKE": "term"}` | `col LIKE '%term%'` |
| Comparison | `{"id >": 200}` | `id > 200` |

REST: `POST /api/2.0/vector-search/indexes/{index_name}/query`

**Tenancy warning (design guidance, not a doc citation):** a metadata filter is *application-enforced*
isolation, not *platform-enforced*. If the app ever constructs the filter from unvalidated input, or omits
it on one code path, tenants leak into each other's results. Two mitigations worth an ADR:
1. Never let callers pass a raw filter. The tenant predicate is injected by a single choke-point helper that
   takes the tenant from the authenticated principal, and callers may only supply *additional* filters.
2. Prefer index-per-tenant for high-assurance tiers, accepting the 500-endpoint/workspace ceiling.
Coordinate with the tenancy workstream (R04) â€” this must match the Unity Catalog isolation story.

### 3.5 Pricing **[R]**
Endpoint has a base price and auto-scales with total index size; scales down when indexes are deleted.
Storage-optimized endpoints cover ~64M vectors @768 dim per "vector search unit". Index storage billed via

module in an OSS accelerator, that is a meaningful "don't turn this on casually" warning to put in the docs.

## 4. Agents / MLflow evaluation

Source: <https://docs.databricks.com/aws/en/mlflow3/genai/eval-monitor/>,
<https://docs.databricks.com/aws/en/mlflow3/genai/eval-monitor/concepts/scorers>,
<https://docs.databricks.com/aws/en/mlflow3/genai/agent-eval-migration>

- Agent Evaluation is now **folded into MLflow 3** under the `mlflow.genai` namespace, via
  `mlflow[databricks]>=3.1`. The older standalone Agent Evaluation API is a migration source. **[V]**
- **LLM judges are a kind of MLflow `Scorer`.** Built-in research-validated judges cover relevance, safety,
  groundedness, correctness. Judges can read the **entire execution trace**, not just input/output. **[V]**
- MLflow 3 adds a production-scale trace ingestion backend, human labelling / feedback collection, and
  evaluation dataset management. **[V]**
- Mosaic AI Agent Framework serves agents on Model Serving. **[V]**

**Hard constraint for us: evaluation and judges are Python-only.** `mlflow.genai.evaluate` is a Python SDK
surface. There is **no REST-equivalent for running evaluation from .NET [G/negative]** â€” I found no such API.

This produces a clean split, and it is the right one:

- **Runtime (production traffic): .NET does it all.** Inference via OpenAI-compatible HTTP; tracing via OTLP.
- **Evaluation (offline, CI): Python.** Traces written by the .NET app are readable by MLflow, so a Python
  job â€” a Databricks job, or a CI step â€” can run judges over production traces without the .NET app ever
  importing MLflow.

That is a genuinely good architecture, not a workaround: it keeps the eval toolchain out of the app's
dependency graph while still letting the app's real traffic feed evaluation.

### 5.1 Rate limits â€” the per-tenant quota question **[V]**

Granularity is **QPM (queries/minute) or TPM (tokens/minute)**, configurable at three levels:
- **Endpoint** â€” ceiling for the whole endpoint
- **User (Default)** â€” default per-user limit
- **Custom** â€” specific users, service principals, or user groups

Constraints: **max 20 rate limits total; max 5 group-specific limits. TPM is not available for custom models
or agents.** Most restrictive applicable limit wins.

**Verdict: AI Gateway does NOT give us per-tenant quotas for free.** The rate-limit key is a Databricks
identity (user / service principal / group), not an application tenant. Getting per-tenant enforcement from
the Gateway would require one Databricks service principal per SaaS tenant â€” and then the **20-limit cap**
means it collapses at 20 tenants. That is not a multi-tenant SaaS quota system.

**We must build quotas in the app tier.** AI Gateway's endpoint-level limit is still worth setting as a
**blast-radius cap** â€” a circuit breaker that protects the spend ceiling when app-tier accounting has a bug â€”
but per-tenant metering, budgets, and 429s belong to Lakewright.NET. Guardrails' PII masking is likewise
useful but **preview, and unavailable on streaming**, so it cannot be the only PII control on a streaming
chat path.

### 6.1 Attribution â€” the gap that decides our design **[V]**

Usage is attributed through `system.serving.endpoint_usage`, which records **token counts per request**.
Attribution keys are the Databricks identity and endpoint â€” **not an application tenant ID**. Combined with:
- system tables readable **only by account admins**,
- inference tables lagging by **~1 hour**,

â€¦this rules out Databricks system tables as the source of truth for per-tenant billing. They are a
**reconciliation** source (month-end truth for what Databricks charged us), not a metering source.

**Per-tenant AI metering must be app-tier**: count tokens from the `usage` field on each response, attribute
to the tenant from the authenticated principal, and persist. Note Â§1.3 â€” **`usage` may be absent on
streaming responses**, so the streaming path needs `stream_options` (Responses API) or a token-estimation
fallback. This is a real correctness trap: a naive implementation meters non-streaming traffic correctly and
silently under-bills every streaming conversation.

## 7. Recommended MINIMAL v0.1 AI scope

**Do not defer AI entirely.** The evidence supports a genuinely small module, because two things collapse
the work: OpenAI compatibility removes the client, and OTLP removes the tracing SDK. Deferring would give up
a strong differentiator ("a .NET SaaS accelerator that already traces to MLflow") for very little saved effort.

**In scope for v0.1 â€” target â‰ˆ 300â€“500 lines:**

1. **`IChatClient` over Databricks**, built on `Microsoft.Extensions.AI.OpenAI` + `OpenAI` with
   `Endpoint = https://{host}/serving-endpoints`. Ship it as a DI extension
   (`AddDatabricksChatClient(...)`) plus options binding. **No bespoke HTTP client, no hand-rolled SSE.**
2. **Pay-per-token foundation-model endpoints only.** No custom endpoints, no provisioned throughput.
   This sidesteps cold starts entirely and keeps setup to "paste a token".
3. **Per-tenant token metering + budget enforcement in the app tier.** A middleware in the `IChatClient`
   pipeline that reads `usage`, attributes to the tenant, and rejects over-budget tenants with 429.
   Must handle the streaming `usage`-absent case explicitly.
4. **OTLP tracing to Databricks**, via `.UseOpenTelemetry()` + the standard OTLP exporter pointed at
   `/api/2.0/otel/v1/traces`. Enrich spans with `session.id` and `user.id`. **Off by default**, one config
   flag to enable.
5. **Endpoint-level AI Gateway rate limit** documented as a required blast-radius cap, set via Bundles
   (coordinate with R06).

**Explicitly out of scope for v0.1:**

- **Vector Search / RAG.** It carries a standing hourly cost with no scale-to-zero, a genuine tenant-isolation
  design problem (Â§3.2), and endpoint-type-dependent filter syntax. It deserves its own milestone with its own
  ADR, not a v0.1 checkbox.
- **Agent Framework, `mlflow.genai.evaluate`, LLM judges.** Python-only; belongs in an optional Python CI job
  reading traces, not in the .NET app.
- **AI Guardrails** â€” Public Preview and unsupported on streaming. Document as available, don't depend on it.
- **Custom / provisioned-throughput endpoints** â€” cold starts and cost complexity.

**Blocking spike before committing (~30 min):** stand up `Microsoft.Extensions.AI.OpenAI` against a real
Databricks workspace and confirm non-streaming chat, streaming chat, tool calling, and embeddings all
round-trip. Everything in item 1 above rests on a compatibility claim I verified from documentation but not
from a running client.
